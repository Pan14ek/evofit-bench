## Readback fields

Each CLI result conforms to `evidence.schema.json` and records:

- `evaluator.id`, `evaluator.obligation_id`, `evaluator.version`, a digest over exact evaluator source files, and the exact configuration digest.
- `architecture.state`, target Git source SHA, state-manifest path/digest, expected source SHA comparison, and whether inspected subject files are dirty.
- Every discovered module identity, inspected Python path and path digest, exact AST import records (file, line, source/target module, imported symbol), and explicit scope uncertainties.
- Evaluator-specific graph/ownership observations, violations, execution status, compliance result, raw diagnostic digest, and known static-analysis limits.

`verify_evidence()` re-reads the architecture-state input manifest, evaluator, config, and inspected subject bytes. Manifest resolution uses an explicit `manifest_root` marker: `subject` paths resolve from the subject checkout; `evidence` paths resolve from the separate evidence bundle (or, for the existing W3 adapter signature, the evaluator-package root). References must be relative and stay inside that root. W3 can use those exact values in its separate sidecar/readback contract; the evaluator result itself does not establish evidence authority.

## Exact-pair boundary

This output identifies an evaluator and architecture obligation. It does **not** assert which fitness representation was used, whether that representation semantically measures the obligation, whether evidence is independently adequate, or whether an obligation is active/mandatory. W3 must bind a result to the exact `(representation_id, obligation_id, architecture_state, target_source_sha)` and independently assess evaluator-to-representation semantic adequacy. A green evaluator exit and `COMPLIANT` result are not pair-level semantic proof.

## W0-approved contract and policy compatibility

The following state-specific policy is encoded by the three evaluator configurations. `ACTIVE` means the obligation is assessed for that source state; `NOT_APPLICABLE` allows diagnostic source inspection without a compliance claim. The graph is a capability graph; imports of configured shared infrastructure are recorded separately and do not create capability edges.

| Architecture state | AC_PUBLIC_API | AC_MODULE_GRAPH | AC_DATA_OWNERSHIP | Allowed capability edges and boundaries |
| --- | --- | --- | --- | --- |
| `A0_1_CAPABILITY_MODULES` | `NOT_APPLICABLE` | `NOT_APPLICABLE` | `NOT_APPLICABLE` | Historical diagnostics only; no A1 compliance claim. |
| `A0_2_PUBLIC_MODULE_APIS` | `ACTIVE` | `NOT_APPLICABLE` | `NOT_APPLICABLE` | Public API rules active. Permit only the exact Reporting → Tasks service query exception described below. |
| `A0_3_GOVERNED_MODULE_GRAPH` | `ACTIVE` | `ACTIVE` | `NOT_APPLICABLE` | `tasks → users`, `tasks → notifications`, `tasks → audit`, `users → audit`, `reporting → tasks`; reject cycles. Reporting's exact service exception remains temporary. |
| `A0_4_REPORT_QUERY_PORT` | `ACTIVE` | `ACTIVE` | `NOT_APPLICABLE` | Same capability graph; ΔA4 removes the Reporting service exception and uses the Task public query contract. |
| `A0_5_MODULE_DATA_OWNERSHIP` | `ACTIVE` | `ACTIVE` | `ACTIVE` | Same graph; ownership evaluator also active. |
| `A1_MODULAR_MONOLITH` | `ACTIVE` | `ACTIVE` | `ACTIVE` | `tasks → users`, `tasks → audit`, `users → audit`, `reporting → tasks`; forbid every direct `tasks → notifications` import, including public imports, after ΔA6. |

Cycles are rejected in active graph states. The Reporting exception is limited to `app.modules.reporting.service` importing `task_summary` from `app.modules.tasks.service`; it is permitted only in `A0_2_PUBLIC_MODULE_APIS` and `A0_3_GOVERNED_MODULE_GRAPH`, and it must fail from A0.4 onward. The capability edge `reporting → tasks` remains allowed after ΔA4 because Reporting continues to depend on the Tasks public query contract.

`app.events` is approved shared infrastructure: its imports from capability files are recorded separately and do not create graph edges. The evaluator does not inspect `app.events` implementation because source scope is limited to capability packages and the one configured model-registry file; W4's event evaluator owns event schema/registration semantics.

The approved table owners are `users → users`, `tasks → tasks`, `notifications → notifications`, and `audit_events → audit`; Reporting owns no table. The sole model-registration exception is the exact path `app/db/model_registry.py`. It accepts only `from app.modules.<capability>.model import <declared ORM model class>` imports, where the class has a literal table declaration in that capability's inspected `model.py`. Star imports, unknown names, other module paths, and non-model capability imports at that registry path are findings. The exception does not permit capability code to import the registry. A shared `Session`, `Base`, migration metadata, and relational foreign keys remain shared infrastructure, not permission for cross-capability reads or writes.

### Evaluator limits and acceptance boundary

The public evaluator validates configured top-level function/type names and `TaskSummary` fields, but not callable signatures, `__all__`, runtime re-exports, or runtime behavior. Static AST checks do not inspect dynamic imports, reflection, dependency injection, raw SQL or `text()` contents, dynamically selected tables, database permissions, or event runtime behavior. The ownership analyzer recognizes configured table/model patterns and ORM calls; unrecognized persistence APIs can escape it. A complete source scope and passing synthetic fixture show evaluator mechanics only, not semantic adequacy or A1 compliance.

The W0 approval freezes these state policies and configuration boundaries; it does not establish that static coverage is sufficient for a scientific fitness claim, provide W3 representation-to-obligation semantic adequacy, or authorize ΔA3/A1 promotion. The ΔA2 source checkpoint has no checked-in A0.2 architecture-state manifest. Any A0.2 run using a separate evidence-input manifest must be labeled as source-bound evaluator evidence, not as a new state manifest or ΔA3 completion. No full A1 compliance is claimed from synthetic tests or A0.1 diagnostics.
