# Пілотний експеримент PILOT-01: перевірка поведінки засобів оцінювання архітектури

## 1. Мета пілотного експерименту

Метою PILOT-01 було перевірити, чи виявляють наявні засоби оцінювання архітектури A0.1 реальне порушення залежностей у вихідному коді та чи зберігаються результати перевірки у відтворюваному вигляді. Дослідницьке питання сформульовано так: чи здатні наявні архітектурні фітнес-представлення виявити контрольоване порушення правила залежностей без втрати походження та перевірності експериментальних свідчень?

Експеримент обмежено поведінкою Import Linter, тесту порядку шарів і перевірки структури модулів для одного втручання у вихідний код. Ефективність адаптації конфігурації фітнес-функцій методом P у ньому не оцінювалася.

## 2. Експериментальне середовище

Вимірювання виконано 19 жовтня 2026 року на macOS 26.6.2 (ARM64; 10 логічних і фізичних процесорів, 16 ГіБ оперативної пам’яті). Використано Python 3.12.14, pytest 8.4.2, Import Linter 2.15, Locust 2.46.6, Docker Engine 29.8.2, Docker Compose 5.5.1 та PostgreSQL 16.15. Ліміти ресурсів контейнерів у Compose не задавалися.

Контрольна версія S0 відповідає коміту `5d285a04da00863088f8cd88a10afb3faaf02ddb`. Втручання S1 збережене окремим комітом `ccbfb002e1fc71d9dcaadf11635d449b8a881cac`, безпосереднім батьком якого є S0. SHA-256 конфігурації фітнес-представлення становив `3f8c952afd00f97f00b84955cc85fdf8dc5cbe32b52e6577173b8aa5a12fbad`, конфігурації Import Linter — `5e938273faa86b4584886e2ede5700b35b064d5e54fe04b0c3d1e50278c64eb0`; обидва значення були однаковими для всіх вимірювань. Надійний зв’язок між комітом вихідного коду та образом застосунку, фактично запущеним у контейнері, не підтверджено; статус ідентичності застосунку у свідченнях EXP-01 залишився `unverified`.

## 3. Опис контрольованих сценаріїв

У сценарії S0 застосовано чисту версію A0.1 без змін. У сценарії S1 до методу `add_notification` репозиторію сповіщень додано відкладений імпорт `notifications.api.router`. Це створює заборонений напрям залежності від репозиторію до API, який порушує наявний контракт `Notifications module internal layering`. Правила оцінювача, конфігурація фітнес-представлення та API-відповіді не змінювалися. Точну зміну наведено у [PILOT_01_S1_FAULT.patch](PILOT_01_S1_FAULT.patch).

У парі S0/S1 перевірено одну незалежну архітектурну інтервенцію: внесення одного порушення залежностей у S1. Для кожної умови виконано по три технічні повтори; вони не є незалежними інтервенціями. У кожному запуску застосовано п’ять користувачів Locust, швидкість запуску одного користувача за секунду, тривалість вимірювання 30 секунд, інтервал збирання метрик одна секунда та нульовий період прогрівання. Використано однакову суміш запитів, описану у [PILOT_01_WORKLOAD.yaml](PILOT_01_WORKLOAD.yaml).

## 4. Методика проведення вимірювань

Пробний запуск S1 для перевірки здійсненності інтервенції виконано до формальних повторів і виключено з їх результатів. Очікувані результати формально зафіксовано перед початком трьох повторів у кожній умові у [PILOT_01_EXPECTATION.md](PILOT_01_EXPECTATION.md). Для кожного повтору зібрано вихідні дані й коди завершення Import Linter та перевірок модулів, навантажувальну статистику Locust, процесні метрики, пакет свідчень EXP-01 і свідчення фітнес-представлення EXP-02. Під час формування таблиці результатів валідатори повторно перевірили пакети й контрольні суми артефактів, а числові метрики окремо перерахували з первинних CSV і звірили з маніфестами.

Повтори є технічними вимірюваннями двох фіксованих станів, а не незалежними архітектурними змінами. Джерело сповіщень S1 продовжувало обслуговувати зафіксоване навантаження; це підтверджує лише спостережувану працездатність у межах цього запуску.

У кожному повторі S1 зафіксовано одне порушення контракту шарів сповіщень; окремий тест порядку шарів для цього модуля завершився невдачею, тоді як п’ять інших архітектурних тестів пройшли. Незалежна перевірка структури модулів пройшла для обох сценаріїв. У всіх шести вимірюваннях навантаження Locust не зареєструвало помилок запитів, а збирач метрик записав 32 вибірки.

## 6. Аналіз отриманих результатів

Спостереження узгоджуються з попередньо зафіксованим очікуванням: наявні засоби виявили одне навмисно введене порушення, не змінивши конфігурації оцінювання. Перевірка структури модулів не призначена для виявлення цієї залежності й залишилася успішною в обох сценаріях. Отже, у межах цього втручання результати показують, що саме контракт Import Linter і пов’язаний тест порядку шарів реагують на заборонений імпорт.

Різниці в затримці, пропускній здатності, процесорному часі та пам’яті подано лише описово. Три повтори кожної умови не є незалежними одиницями архітектурної еволюції, тому статистичні висновки про перевагу одного сценарію не робляться.

## 7. Обмеження пілотного експерименту

Ідентичність вихідного коду контейнера застосунку не була підтверджена надійним зв’язком між комітом і образом. Експеримент охоплював один контракт залежностей, коротке навантаження з п’ятьма користувачами й одну незалежну архітектурну інтервенцію. Зібрані EXP-01/EXP-02 свідчення не встановлюють незалежну семантичну коректність, `Coverage_P` або `Coverage_ref`; ці показники залишаються відповідно `not_assessed` і `not_established`. PILOT-01 перевіряв наявні засоби оцінювання, а не ефективність адаптації методом P; він не встановлює статистичної значущості. Не проводилися людська перевірка B1, вимірювання DA01 чи оцінювання G1/G4. Попередній пробний запуск S1 для перевірки здійсненності виконано до формальних повторів і виключено з результатів.

## 8. Проміжні висновки

PILOT-01 надає відтворювані DEVELOPMENT-свідчення того, що наявний Import Linter виявив задане порушення залежностей між репозиторієм і API в усіх трьох повторах S1, тоді як S0 пройшов наявні архітектурні перевірки. Матеріал розділу 5 призначено для представлення фактичних результатів у відповідному підрозділі рукопису. Пілот перевіряє поведінку наявних засобів оцінювання фітнес-конфігурації; він не оцінює ефективність адаптації методом P, не встановлює статистичної значущості й не доводить `Coverage_ref`. Для PILOT-02 необхідно окремо забезпечити готовність P до виконання, точну базову конфігурацію B0 і доказово обґрунтований кандидат адаптації, завершити умови G1 та отримати дозвіл G4 на вимірюване порівняння.
